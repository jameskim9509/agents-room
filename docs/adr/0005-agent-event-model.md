# ADR 0005: AgentEvent 모델

## 상태

Accepted (2026-10-23 팀 결정).
Jira가 정한 것은 "공통 AgentEvent"(SCRUM-11, 66), 정규화(SCRUM-23), 지어내지 않는다는 원칙(SCRUM-19, 21, 27)이다. 모델의 형태는 정하지 않았으므로, 아래의 이름, 단위, 전이는 이 ADR이 정한다.
Sprint 0 계약(프레임, 스냅샷, `authStatus`, 프로젝트 오류 코드, 전이표 보완)을 반영했다 (2026-10-25). 명령을 확인하는 순서를 결정 2에 더했다 (2026-10-26, 런타임 PR). Codex 연결을 구현하며 전이표의 세부(실행 중 `stopAgent`, 단계, 세션 열기 전 update, 프롬프트 오류, 실행 밖 권한 요청, 어댑터가 거둔 권한 요청, SDK가 건너뛰는 메시지)와 설정 상태가 바뀔 때의 `agentsUpdated`를 더했고, 청크 마스킹의 한계를 결정 11에 적었다 (2026-10-26, ACP PR). 계약(`core/asyncapi.yaml`)은 바꾸지 않았다. `core/asyncapi.yaml`이 이 ADR을 따른다.

## 날짜

2026-10-21

## 맥락

- 업스트림 `AgentEvent`(`core/src/provider.ts`)의 kind는 10개다: `toolStart`, `toolEnd`, `turnEnd`, `subagentStart`, `subagentEnd`, `subagentTurnEnd`, `progress`, `permissionRequest`, `sessionStart`, `sessionEnd`.
- 이 모델은 toolId를 `hook-${Date.now()}`로 지어내고 `progress`를 버린다. `AgentActivityStatus`(`core/asyncapi.yaml`)는 `active`와 `waiting`뿐이라 실패와 취소를 표현하지 못한다. `permissionRequest`에는 payload가 없고, 권한 요청(Permission request)에 응답하는 ClientMessage도 없다. `runInBackground` 같은 Claude 전용 필드가 있다.
- ACP v1에는 `sessionUpdate` 판별자 14종, `StopReason` 5종, `ToolKind` 10종, `ToolCallStatus` 4종(`cancelled` 없음), 권한 옵션 kind 4종이 있다 ([schema.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/schema/v1/schema.json), [Tool Calls](https://agentclientprotocol.com/protocol/tool-calls), [Prompt Turn](https://agentclientprotocol.com/protocol/prompt-turn)).

## 결정

1. 공통 필드(envelope)는 `{ projectId, agentId, sessionId | null, runId | null, seq, receivedAt, kind, data }`이고, kind는 아래 kind 표와 같다. `seq`는 에이전트마다 1부터 늘어나는 수신 순번이다. `receivedAt`은 런타임이 원본 메시지를 받은 시각이며 epoch 밀리초 정수다. 내용 이벤트는 ACP v1 판별자와 1:1로 대응하고, agents-room은 상태, 생명주기, 실행(Run), 권한, 진단 이벤트만 더한다. 생명주기의 `authStatus {kind, label}`은 어댑터가 보고한 인증 상태다 (codex-acp `_auth/status_update`). `account.email` 같은 신원 필드는 버리고, `label`은 그대로 보여준다 ([ADR 0004](0004-model-authentication.md)). 클라이언트가 광고해야 오는 `notice`, `compaction_update`, `compaction_summary_chunk`는 MVP에서 받지 않는다.
2. 렌더러가 런타임에 보내는 명령은 `openProject`, `relocateProject`, `saveAgentConfig`, `checkConnection`, `startAgent`, `stopAgent`, `sendPrompt`, `cancelRun`, `respondPermission`이다. `cancelRun`은 실행만 멈추고(SCRUM-24의 "중지"), `stopAgent`는 어댑터 프로세스를 끝낸다. 런타임은 명령을 형식(`INVALID_MESSAGE`) → id(`UNKNOWN_PROJECT`, `UNKNOWN_AGENT`, `UNKNOWN_PERMISSION`) → 상태와 구현 여부(`INVALID_STATE`, `NOT_IMPLEMENTED`) 순서로 확인하고, 처음 걸린 검사의 이유로 거절한다. Sprint 0은 `relocateProject`, `saveAgentConfig`, `cancelRun`을 정의만 하고, id 확인을 통과하면 `commandRejected {reason: NOT_IMPLEMENTED}`로 답한다. 모르는 id를 담았으면 그 전에 `UNKNOWN_PROJECT`나 `UNKNOWN_AGENT`로 거절한다. 런타임이 보내는 프레임은 아래 프레임 표와 같다. 에이전트에 속하지 않는 결과(프로젝트 열기 등)는 AgentEvent가 아니라 별도 프레임이다. `connectionChecked`는 모든 렌더러에 보낸다. 에이전트의 설정 상태(`readiness`)가 바뀌면(어댑터가 "로그인 안 됨"을 알렸을 때 `auth_required`, 로그인이 보고되면 다시 `configured`, 설치를 찾지 못하거나 띄울 실행 파일이 없으면 `executable_missing`, 어댑터가 설정한 인증 방식을 광고하지 않으면 `unsupported`) 런타임은 `agentsUpdated`를 다시 보낸다. `connectionChecked`의 `readiness`는 그 확인이 본 것을 반영한 이 값이다. 그래서 카드와 확인 결과가 다르지 않다. 현재 프로젝트에 `offline`·`error`가 아닌 에이전트나 연결 확인이 있는 동안 다른 프로젝트를 여는 `openProject`는 `INVALID_STATE`다 (열린 프로젝트는 하나다). 렌더러가 WebSocket에 연결될 때마다(재연결 포함) 런타임은 `snapshot`을 먼저 보내고 그다음부터 이벤트를 보낸다 (업스트림 `agentActivityResend.ts`의 개념). 렌더러는 에이전트별 상태를 스냅샷으로 바꾸고, `seq`가 그 에이전트의 `lastSeq` 이하인 이벤트는 버린다. `lastSeq`는 첫 이벤트 전에는 0이다. 스냅샷의 `project`는 `currentProjectId`가 null이 아닐 때만 있다. 지난 이벤트는 다시 보내지 않으므로 Detail Panel이 보여주는 것은 모두 `AgentSnapshot`에 담는다: 열린 세션의 세션 단위 보고 마지막 값(`session`: agentInfo, modes, configOptions, 현재 mode, 제목, 명령 목록, Plan, 사용량), 마지막 세션 종료(`sessionEnd`), 마지막으로 끝난 실행(`lastRun`과 `prompt`), 최근 이벤트 꼬리(`recentEvents`). 꼬리는 메모리에만 두고 저장하지 않는다. 생각 청크는 빼고, kind와 `messageId`(없으면 실행)가 같은 연속한 텍스트 청크는 text를 이은 이벤트 하나로 합쳐 최대 200개를 남긴다. 그보다 오래된 이벤트와 생각 청크는 재연결 뒤에 보이지 않는다.
3. 실행은 `session/prompt` 1회다. `runId`는 런타임이 발급한다. 실행 밖에서 온 update(세션 단위 update, 응답 뒤에 늦게 온 update)는 `runId = null`이다. 프롬프트 단위로 잡아야 늦게 온 이벤트(SCRUM-24)와 비정상 종료(SCRUM-47)를 해당 실행에 귀속할 수 있다. Jira의 "실행"이 가리키는 단위는 [용어집](../architecture.md#용어집), 식별자 정의는 [식별자](../architecture.md#식별자)에 있다.
4. 에이전트 상태는 런타임이 계산하고 `agentStatusChanged`로 보낸다. 렌더러는 상태를 다시 계산하지 않는다. 전이는 아래 전이표와 같다. 값, 표시, Jira 상태어(SCRUM-6)와의 대응은 [ux.md#상태-어휘](../ux.md#상태-어휘)에 있다. `error`로 가는 전이는 모두 어댑터 프로세스 트리를 끝내므로, `offline`과 `error`에서 도는 프로세스는 연결 확인의 것뿐이다. `stopAgent`는 `offline`·`error`가 아닌 모든 상태에서 받는다. 실행 중이면 먼저 [ADR 0003](0003-acp-integration.md) 결정 7대로 취소하고, 정해진 시간만 기다린 뒤 프로세스 트리를 끝낸다. 취소 응답이 시간 안에 오지 않아 강제로 끝낼 때도 같은 경로를 쓴다 (SCRUM-24). 실행 중에 받은 `stopAgent`는 그동안 `cancelling`이고, 멈추는 동안의 프로세스 종료는 요청한 종료다(종료 코드와 상관없이 `sessionEnded {reason: stopped}`). `agentError`의 `stage`는 시작 중이면 그 시작 단계, `ready`이면 `running`, 실행 중(`running`, `awaiting_permission`, `cancelling`)이면 `prompt`다. `agentStarting {stage: authenticate}`는 어댑터의 로그인을 실제로 시작할 때만 보낸다 ([ADR 0004](0004-model-authentication.md) 인증 방식 표). `checkConnection`은 `offline`·`error`에서만 받는다. 어댑터를 띄워 `initialize`까지만 하고 끝내며, 그동안 상태는 바뀌지 않고 그 프로세스가 에이전트의 프로세스 1개다. 결과와 실패(비정상 종료, 형식 오류 포함)는 `connectionChecked`로만 알린다. `initialize`에 답한 뒤 인증 상태를 기다리는 동안 어댑터가 끝나거나 ACP가 아닌 줄을 쓰면 `PROCESS_EXITED`나 `PROTOCOL_ERROR`(stage `initialize`)다. `disconnected`의 전이는 post-MVP(SCRUM-48)에서 정한다.
5. 실행 결과는 `stopReason`으로 정한다: `end_turn` → `completed`, `cancelled` → `cancelled`, `refusal` → `refused`, `max_tokens`·`max_turn_requests` → `limit_reached`, `session/prompt` 오류 응답이나 실행 중 프로세스 종료 → `failed`. 사용자가 중지를 요청했어도 실제 `stopReason`이 `end_turn`이면 `completed`다 (SCRUM-24 "실제 결과에 맞게"). `session/prompt` 오류 응답의 `errorCode`는 `-32000`이면 `AUTH_REQUIRED`, 그 밖에는 `PROMPT_FAILED`다. 세션은 그대로이므로 상태는 `ready`로 돌아가고 `agentError`는 보내지 않는다. ACP v1이 정하지 않은 `stopReason`은 `failed`다(`stopReason`은 받은 그대로 보낸다). 실행 종료를 타이머로 추정하지 않는다. 업스트림의 휴리스틱 타이머(권한 7초, text-idle 5초)는 ACP 에이전트에 쓰지 않는다.
6. Tool 호출(Tool call): `toolCall`과 `toolCallUpdate`는 `toolCallId` 기준으로 부분 병합한다. 같은 `toolCallId`의 update는 새 Tool 호출을 만들지 않는다 (SCRUM-27). `content`와 `locations`는 이전 값을 대체한다. `rawInput`과 `rawOutput`은 보고되면 바꾸고, `vendorMeta`는 마지막으로 받은 `_meta` 그대로다 (병합하지 않는다). `kind`나 `status`가 없으면 런타임 상태에는 `null`로 두고, 메시지에서는 그 필드를 뺀다. 렌더러는 "미지정"으로 쓴다 (ACP 기본값을 사실로 저장하지 않는다). 실행이 끝났을 때 끝나지 않은 Tool 호출은 결과가 `cancelled`면 `derivedStatus: cancelled`, 그 밖이면 `derivedStatus: incomplete`로 표시하고, 둘 다 클라이언트가 판단한 값이라고 밝힌다. 행동 표시는 [ux.md#행동-매핑](../ux.md#행동-매핑)에 있다.
7. 권한 요청은 상태를 가진 엔티티로 다룬다: `{permissionId, agentId, sessionId, runId, toolCall, options[{optionId, name, kind}], state: pending | answered | cancelled}`. 명령 `respondPermission {permissionId, optionId}`를 새로 만든다. 렌더러는 사용자가 고른 선택지만 보낸다. `permissionResolved`의 `optionId`는 `outcome: selected`일 때만 있다 (ACP `RequestPermissionOutcome`과 같다). `cancelled` 응답은 런타임이 실행을 취소하거나 에이전트를 종료할 때만 보낸다 ([ADR 0003](0003-acp-integration.md) 결정 7). 어댑터가 대기 중인 요청을 거두면(`$/cancel_request`. codex-acp는 실행이 취소되거나 app-server 연결을 잃으면 거둔다) SDK가 그 요청에 `-32800`으로 답하고, 런타임은 `permissionResolved {outcome: cancelled}`로 닫는다. 그 요청에 온 `respondPermission`은 `UNKNOWN_PERMISSION`이다. 어댑터가 읽지 않을 답을 `selected`로 보여주지 않기 위해서다. `respondPermission`의 `optionId`가 그 요청의 선택지가 아니면 `INVALID_MESSAGE`로 거절한다. 계약이 모르는 kind의 선택지는 보내지 않으므로 고를 수 없다. 실행 밖에서, 또는 `cancelling` 중에 온 요청은 `permissionRequested`로 보여준 뒤 바로 `permissionResolved {outcome: cancelled}`로 닫는다. MVP 기본 정책: 어댑터가 보낸 권한 요청은 모두 사용자에게 보여주고, 자동으로 허용하지 않으며, 대화상자를 닫으면 요청은 대기 상태로 남는다 (SCRUM-15, 33). 에이전트별 세부 정책은 post-MVP다 (SCRUM-62).
8. 오류 코드 enum은 아래 오류 코드 표다 (이 ADR이 홈이다). 감지원은 [ADR 0003](0003-acp-integration.md)과 [ADR 0004](0004-model-authentication.md), 문구는 [ux.md#문구-목록](../ux.md#문구-목록)에 있다. 프로젝트 열기 실패는 에이전트 오류가 아니므로 `ProjectErrorCode`를 따로 쓴다. 검사 순서대로 `PATH_NOT_ABSOLUTE`, `PATH_NOT_FOUND`, `PATH_NOT_DIRECTORY`, `PATH_NOT_READABLE`이다. 런타임이 명령을 받지 않을 때는 `commandRejected`의 `RejectReason`을 쓴다: `UNKNOWN_PROJECT`, `UNKNOWN_AGENT`, `UNKNOWN_PERMISSION`, `INVALID_STATE`, `INVALID_MESSAGE`, `NOT_IMPLEMENTED`. 거절한 명령은 아무것도 바꾸지 않는다.
9. 지어내지 않기: Plan은 받은 목록 전체로 바꾼다. 우선순위는 어댑터가 만든 값일 수 있다 (codex-acp는 `medium`으로 고정한다). 컨텍스트 게이지는 `usage.used`/`usage.size`로만 그리고, 비용은 `cost`가 있을 때만 보여준다. 제목은 `sessionInfo.title`에서 온다. 생각 청크는 live로만 보여주고 저장하지 않는다 (SCRUM-16 범위 제외, SCRUM-52). vendor `_meta`(예: `claudeCode.parentToolUseId`, `terminal_output`)는 선택적인 보강 정보로만 쓰고 "어댑터 제공 정보"로 표시한다. Tool 호출의 `_meta`는 `vendorMeta`로 보낸다.
10. 서브에이전트(Sub-agent) 캐릭터는 post-MVP다 (SCRUM-56, 2026-10-22 팀 결정). 그때도 ACP가 검증된 부모·자식 세션 ID를 보고할 때만 만든다 (SCRUM-21). MVP에서는 Agent나 Task Tool 호출을 일반 Tool 호출로 보여주고, claude-agent-acp의 `_meta.claudeCode.parentToolUseId`가 있으면 Detail Panel 안에서 묶어 보여줄 수 있다. 자식 세션을 알리는 방법은 [Subagents RFD](https://agentclientprotocol.com/rfds/subagents)(Draft. 스키마는 1.24.0부터 unstable)에 있다: `clientCapabilities.subagents`를 광고하면 부모 세션의 `subagent_update`가 자식 `sessionId`를 알린다 (SCRUM-56, post-MVP). 이를 쓰려면 SDK를 고치거나 얇은 클라이언트가 필요하다 (ADR 0003).
11. 계약은 `core/asyncapi.yaml` 하나다. AsyncAPI 3.0.0으로 고정한다 (Modelina 5.10.1은 3.x 중 3.0.0만 지원한다). Modelina로 TS(렌더러)와 Java(런타임) 바인딩을 생성하고, 업스트림의 CI drift check를 유지한다. 손으로 맞춘 DTO는 drift가 생긴다 (업스트림 `AgentCreated`, [upstream.md#알려진-불일치](../upstream.md#알려진-불일치)). broadcast는 타입 검사를 한다. 어댑터에서 온 값은 모두, 진단 `message`와 함께 [ADR 0004](0004-model-authentication.md) 결정 8의 마스킹 계층을 거친 뒤 보낸다. Tool 제목·위치·`content`·`rawInput`·`rawOutput`·`vendorMeta`, 청크 텍스트, Plan 항목, 세션 제목, 명령 목록, 권한 선택지 이름, `agentInfo`, 인증 방식 이름, `modes`, `configOptions`, `AuthStatus.label`이 그 예이고, 여기에 없는 값도 마찬가지다. 청크 텍스트는 청크마다 따로 마스킹한다. 그래서 두 청크에 나뉘어 온 비밀은 실시간 이벤트에서 조각으로 보일 수 있고, 렌더러가 이어 붙이면 화면에 다 보인다. 스냅샷의 `recentEvents`만 합친 글을 다시 마스킹해서 가린다 (알려진 한계. 청크의 꼬리를 다음 청크까지 잡아 두고 이음매를 마스킹하는 방법은 후속 작업이다). `message`는 문구 아래의 원인 한 줄에만 쓰고 UI 문구로 쓰지 않는다. 선택 필드에 값이 없으면 메시지에서 뺀다. `null`은 `sessionId`, `runId`, `modelId`, `currentProjectId`처럼 필수이고 값이 없을 수 있는 문자열에만 쓴다. TS 바인딩(`core/src/messages.ts`)은 커밋한다. TS 바인딩은 두 union에서 `x-legacy`가 아닌 원소만 모은 `RuntimeServerMessage`와 `RuntimeClientMessage`도 선언한다. 데스크톱 렌더러는 런타임 소켓을 이 타입으로 다룬다. Java 바인딩(`npm run asyncapi:generate:java -- --out <dir>`, 패키지 `agentsroom.contract`, Jackson 주석)은 런타임 빌드가 만들고 커밋하지 않는다. Java `AgentEvent` 인터페이스는 envelope 필드마다 getter와 setter를 선언하므로, Event normalizer는 구체 이벤트 클래스를 몰라도 `seq`와 `runId`를 붙인다. 이 ADR과 [ux.md](../ux.md)의 규칙 중 스키마에 넣은 것은 다음뿐이다: `seq` ≥ 1, `lastSeq` ≥ 0, `palette` 0–5, `hueShift` 0 또는 45–315, `recentEvents`는 최대 200개이고 `agentThoughtChunk`가 없다, 프로젝트가 열려 있을 때만 `project`가 있고 열려 있지 않으면 `agents`가 비어 있다, `outcome: selected`일 때만 `optionId`가 있다. JSON Schema로 쓸 수 있지만 넣지 않은 규칙(예: `lastError`는 `error`에서만 있다)과 쓸 수 없는 규칙(청크 병합, `seq` 순서)은 런타임 테스트가 확인한다. 조건 규칙은 TS·Java 타입에 나타나지 않는다 (`project`와 `optionId`는 타입에서 선택 필드다). 모든 프레임, 명령, kind의 예시와, 위 규칙마다 그것을 어기는 예시가 `core/fixtures/`에 있고, `npm run contract:check`가 ajv strict 모드로 검사한다 (스키마에 모르는 키워드가 있으면 실패한다). 업스트림 프레임은 같은 union에 `x-legacy: true`로 남기고, Java 바인딩에는 넣지 않는다. 업스트림의 `subagent*`, `team*`, `isTeammateSpawn`, `runInBackground`, `isExternal`, `STATUS_TO_TOOL` 영어 접두어 해석, hooks와 JSONL 이벤트는 버린다.

## 검토한 대안

### 업스트림 AgentEvent 유지

- 장점: 렌더러의 기존 처리 코드(`useExtensionMessages.ts`)를 그대로 쓸 수 있다.
- 단점: 권한 id와 옵션이 없고, 실패와 취소를 표현할 수 없으며, 지어낸 id와 Claude 전용 필드가 남는다.
- 판단: 채택하지 않는다.

### 원시 ACP JSON 전달

- 장점: 변환 계층이 없다.
- 단점: 렌더러가 프로토콜 버전과 vendor `_meta`에 묶이고, 한 곳에서 마스킹할 수 없으며, 생명주기 정보가 없다.
- 판단: 채택하지 않는다.

### 프로세스나 세션 수명 단위의 Run

- 장점: 식별자가 하나 줄어든다.
- 단점: 요청마다 결과(완료, 실패)를 줄 수 없고, 취소 뒤에 늦게 온 이벤트를 구분할 수 없으며, SCRUM-53처럼 완료·실패 상태로 실행을 찾을 수 없다.
- 판단: 채택하지 않는다.

## 결과

- 좋은 점: 매핑이 1:1이라 어댑터가 보고한 것 이상을 만들지 않는다. 실행기를 추가해도 렌더러를 바꾸지 않는다. 턴 종료 감지가 한 곳에 모여 있어, v2(idle `state_update`로 턴 종료를 알린다)로 옮길 때 실행 경계 규칙은 그 한 곳만 바뀐다.
- 비용과 위험: 렌더러의 `useExtensionMessages.ts`를 다시 써야 한다. 범용 작업 표시(SCRUM-27)와 새 아이콘 스프라이트가 필요하다. 생성된 Java 클래스는 `required`를 강제하지 않는다 (Jackson 3 기본값에서 빠진 필드는 `null`이나 0이 된다). 범위와 개수(`minimum`, `maximum`, `maxItems`), 조건과 금지 규칙(`if`/`then`/`else`, `not`)도 강제하지 않는다. gateway가 명령을 따로 검증해야 하고, 런타임이 보내는 프레임이 이 규칙을 지키는지는 런타임 테스트가 확인해야 한다.
- 후속 작업: `server/`와 `adapters/vscode/`를 지울 때 `x-legacy` 프레임도 지운다. 청크 경계에 걸친 비밀의 실시간 마스킹(결정 11). CI에 `npm run contract:check`를 넣고, 런타임 Gradle 빌드가 Java 바인딩을 생성하게 한다.

### 열린 질문

- notice와 compaction을 언제 광고할지.
- codex-acp가 표준 `subagent_update`를 보내는지. 문서에는 초기 AIR 초안의 이벤트 이름이 있다 (미검증, 실제 테스트 필요).
- 이력 저장(SCRUM-52)의 마스킹과 보존 정책.
- 메시지 청크를 묶는 단위 (SCRUM-28: 묶어도 주요 상태 전환은 빠뜨리지 않는다).
